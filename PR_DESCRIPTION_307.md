This PR closes #307 by teaching codegraph to recognize and resolve routes registered through Hono's sub-router and `app.route` composition pattern. Until now, the framework extractor only harvested routes attached directly to the receiver variable named `app` or `router`, so any route defined on a separate sub-router instance and mounted onto the main app was silently dropped from the index.

The motivation is straightforward. Hono projects typically split a server across files like `routes/users.ts` that defines `const userRoutes = new Hono(); userRoutes.get('/me', getMe);` and `server.ts` that calls `app.route('/users', userRoutes)`. Static analyzers that only see the literal `app.method(...)` calls fail to attribute `GET /users/me` to the codebase at all. The same shape shows up in Express via `Router()` instances and in Hono whenever a developer composes routers, which is the dominant pattern in the wild.

The implementation lives entirely inside `src/resolution/frameworks/express.ts`, with no changes to the public CLI or the resolution pipeline contract. First, the framework detector now also recognizes `hono` and `new Hono(...)` constructs, so a project that depends on Hono is routed to the same extractor as Express. Second, the route-extraction regex was widened so it captures any receiver name rather than hardcoding `app` or `router`. A route registered as `userRoutes.get('/me', getMe)` is now picked up the same way as `app.get('/me', getMe)`. Third, a new `postExtract(context)` hook runs after per-file extraction and stitches mounted prefixes across the file boundary.

The cross-file stitching works in three steps. It scans every JavaScript and TypeScript file in the project for the same family of route registrations and for `app.route(prefix, child)` mount calls. It then resolves which child router is owned by which file by following import bindings and qualified names. Finally, it walks the resulting prefix graph in topological order and rewrites each route entry so the mounted prefix is prepended to the route name, producing entries like `GET /users/me` from a `userRoutes.get('/me', ...)` declared in `routes/users.ts` that is re-exported into `server.ts` as `app.route('/users', userRoutes)`. The three new helpers `parseRouteFromQualifiedName`, `joinRoutePath`, and `resolveImportedFile` keep that logic small and readable.

Two new tests in `__tests__/frameworks.test.ts` cover the in-file case. They assert that a non-`app`/`router` receiver such as `userRoutes` produces the expected route entry and that the prefix is preserved. The new suite in `__tests__/frameworks-integration.test.ts` covers the cross-file case end to end. It indexes a synthetic project with a Hono app defined in one file and a sub-router defined in another, with `app.route` mounting them together, and verifies that the resulting index contains both `GET /health` and `GET /users/me` rather than just the directly-attached routes.

The change is fully backward compatible. Projects that do not depend on Hono and do not compose sub-routers see the exact same extraction output as before, because `postExtract` is a no-op when it cannot find any `app.route` mount points. Existing route nodes are rewritten in place only when a matching mount prefix is found, so unrelated routes are untouched. The dependency check is additive: `hono` is added alongside the existing `express` and `koa` checks, never replacing them.

Validation was performed against the latest `main` baseline. The full Jest suite passes, with the two new Hono suites being the only additions. Manual smoke testing against a representative three-file Hono project confirmed that previously-dropped routes now appear with the correct mounted paths and that route lookups inside the MCP server return concrete symbols for them.

Closes #307.
